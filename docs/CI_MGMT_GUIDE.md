# Updating release.yml via Pulumi ci-mgmt

Since `release.yml` is autogenerated by [Pulumi's ci-mgmt](https://github.com/pulumi-labs/ci-mgmt) tool, direct modifications will be overwritten. Instead, use the `.ci-mgmt.yaml` configuration file to customize the generated workflows.

---

## ⚡ Quick Start: Generate Workflows Locally

Run this command to regenerate `release.yml` and other workflows:

```bash
go run github.com/pulumi-labs/ci-mgmt/provider-ci@master generate \
  --name duplocloud/pulumi-duplocloud \
  --out . \
  --template bridged-provider \
  --config .ci-mgmt.yaml \
  --skip-migrations
```

Then review changes:
```bash
git diff .github/workflows/
```

**Note:** The `--skip-migrations` flag is essential to avoid Go module errors.

---

## Overview

The Pulumi ci-mgmt tool:
- Generates consistent GitHub Actions workflows for all Pulumi providers
- Reads configuration from `.ci-mgmt.yaml` in the repository root
- Allows overriding default values for customization
- Regenerates workflows regularly via automation
- Located at: https://github.com/pulumi-labs/ci-mgmt (moved from pulumi/ci-mgmt)

## Configuration File: `.ci-mgmt.yaml`

### Location
```
pulumi-duplocloud/
├── .ci-mgmt.yaml          ← Configuration file
├── .github/
│   └── workflows/
│       ├── release.yml    ← Generated from ci-mgmt
│       ├── upgrade-provider.yml
│       └── ...
```

### Basic Structure

```yaml
# Provider name (without "pulumi-" prefix)
provider: duplocloud

# Environment variables for tests
env:
  TF_APPEND_USER_AGENT: pulumi
  PULUMI_API: https://api.pulumi-staging.io

# Enable/disable features
lint: true
docker: false

# Custom setup script for tests
setup-script: ./scripts/ci-setup.sh

# Language SDKs to generate
languages:
  - go
  - python
  - nodejs
  - dotnet

# Registry configuration
registries:
  pypi:
    enabled: true
    token: PYPI_API_TOKEN
  npm:
    enabled: true
    token: NPM_TOKEN
  nuget:
    enabled: true
    token: NUGET_PUBLISH_KEY
```

## Making Changes to release.yml

### Step 1: Check Current Configuration

Look for `.ci-mgmt.yaml` in the repository root:

```bash
cat .ci-mgmt.yaml
```

If it doesn't exist, create one based on the template below.

### Step 2: Modify `.ci-mgmt.yaml`

Add or update configuration options. Common customizations:

**Example: Add custom environment variables**
```yaml
provider: duplocloud

env:
  TF_APPEND_USER_AGENT: pulumi
  PULUMI_API: https://api.pulumi-staging.io
  CUSTOM_VAR: value
  ANOTHER_VAR: another_value
```

**Example: Enable/disable linting**
```yaml
lint: true  # Enable code linting in CI
```

**Example: Configure publishing**
```yaml
publish:
  pypi:
    enabled: true
    packageName: pulumi-duplocloud
  npm:
    enabled: true
    packageName: '@duplocloud/pulumi'
  nuget:
    enabled: true
    packageName: DuploCloud.Pulumi
```

### Step 3: Regenerate Workflows

#### Option A: Manual Generation (Local) - **RECOMMENDED FOR QUICK TESTING**

Use the `--skip-migrations` flag to avoid Go module resolution issues:

```bash
# Clone the repository
git clone https://github.com/duplocloud/pulumi-duplocloud.git
cd pulumi-duplocloud

# Run the ci-mgmt provider-ci tool to generate workflows
go run github.com/pulumi-labs/ci-mgmt/provider-ci@master generate \
  --name duplocloud/pulumi-duplocloud \
  --out . \
  --template bridged-provider \
  --config .ci-mgmt.yaml \
  --skip-migrations

# Review changes
git diff .github/workflows/release.yml
```

**Key Flag Explanation:**
- `--skip-migrations`: Skips Go module dependency resolution and code-level migrations. Since we only need workflow generation, this avoids errors and is much faster.

#### Option B: Automatic via GitHub Actions (RECOMMENDED FOR CI/CD)

1. **Create a PR** with changes to `.ci-mgmt.yaml`
2. **Trigger the automation:**
   - Go to GitHub Actions → "Update Workflows, Single Bridged Provider"
   - Enter: `duplocloud` as the provider name
   - Run the workflow

3. **Review the changes**
   - ci-mgmt will generate updated `release.yml`
   - Changes appear in the PR automatically
   - No local environment setup needed

#### Alternative: Clone ci-mgmt Locally

```bash
# Clone ci-mgmt repository
git clone https://github.com/pulumi-labs/ci-mgmt.git
cd ci-mgmt

# Run generation for your provider
go run ./provider-ci generate \
  --name duplocloud/pulumi-duplocloud \
  --out /path/to/pulumi-duplocloud \
  --template bridged-provider \
  --config /path/to/pulumi-duplocloud/.ci-mgmt.yaml \
  --skip-migrations

# Review changes in your provider repo
cd /path/to/pulumi-duplocloud
git diff .github/workflows/release.yml
```

### Understanding the `--skip-migrations` Flag

**What it does:**
- Generates workflow files ONLY
- Skips Go module dependency resolution
- Skips provider code-level migrations/updates
- Fast and avoids environment issues

**Why use it:**
- ✅ Avoids Go module resolution errors
- ✅ Avoids missing local SDK path issues
- ✅ Generates workflows 3-5x faster
- ✅ Works in any environment without setup

**When to NOT use it:**
- ❌ If you need to apply code migrations from ci-mgmt
- ❌ If you need to update provider code structure
- ❌ For full provider regeneration

For workflow-only generation (which is 99% of use cases), always use `--skip-migrations`.

## Common Customizations

### 1. Add Build Steps to release.yml

**In `.ci-mgmt.yaml`:**
```yaml
provider: duplocloud

# Custom build steps (if supported by ci-mgmt template)
buildSteps:
  - name: Custom Pre-Build
    run: ./scripts/pre-build.sh
  - name: Custom Post-Build
    run: ./scripts/post-build.sh
```

### 2. Add Slack Notification

We already handle this separately in `notify-release.yml` (recommended approach).

If you need it in release.yml itself, override the template:
```yaml
provider: duplocloud
notifySlack: true
slackWebhook: SLACK_WEBHOOK_URL
```

### 3. Configure Publishing

## Advanced: Override Workflow Locally

If ci-mgmt doesn't support your customization, you can:

1. **Create a separate workflow** that extends release.yml
2. **Use a workflow_run trigger** to run after release.yml completes

Example: `release-custom.yml`
```yaml
name: Custom Release Steps

on:
  workflow_run:
    workflows: [release]
    types: [completed]

jobs:
  custom_steps:
    if: github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Run custom post-release steps
        run: ./scripts/post-release.sh
```

This way:
- release.yml is managed by ci-mgmt
- Your customizations run after release completes
- Changes don't get overwritten

## Workflow: Making Changes

```
1. Edit .ci-mgmt.yaml locally
   └─ Add/modify configuration

2. Commit and push to a branch
   └─ git push origin feature/update-ci-config

3. Create Pull Request
   └─ PR is created on GitHub

4. Trigger ci-mgmt automation
   └─ GitHub Actions → "Update Workflows, Single Bridged Provider"
   └─ Enter provider name: duplocloud
   └─ Workflow regenerates release.yml

5. Review changes
   └─ Compare old vs new release.yml
   └─ Verify configuration applied correctly

6. Merge PR
   └─ Both .ci-mgmt.yaml and generated release.yml are committed
```

- Any manual changes will be overwritten
- Always update `.ci-mgmt.yaml` instead

- `.github/workflows/upgrade-provider.yml`
- `.github/workflows/auto-release.yml`
- `.github/workflows/notify-release.yml`
- Any custom workflows you create

## Example: Complete .ci-mgmt.yaml

```yaml
# Provider configuration for DuploCloud
provider: duplocloud

# Environment variables for CI/CD
env:
  TF_APPEND_USER_AGENT: pulumi
  PULUMI_API: https://api.pulumi-staging.io
  GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

# Enable linting
lint: true

# Languages to generate SDKs for
languages:
  - go
  - python
  - nodejs
  - dotnet

# Publishing configuration
registries:
  github:
    enabled: true
  pypi:
    enabled: true
    token: PYPI_API_TOKEN
  npm:
    enabled: true
    token: NPM_TOKEN
  nuget:
    enabled: true
    token: NUGET_PUBLISH_KEY

# Test configuration
tests:
  enabled: true
  setup: ./scripts/ci-setup.sh
  timeout: 3600

# Additional configuration
publishPrerelease: false
skipChecksOnPullRequest: false
```

This will generate a release.yml with all the specified configurations.
